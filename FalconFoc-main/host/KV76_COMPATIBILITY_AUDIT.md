## 2. KV76有效配置：以代码覆盖段为准

`BLDCMotor.h`保留历史PM3510/rb/5210定义，后面的 `Active motor: LJW8115 KV76` 段覆盖其中若干值。只看前面的宏或旧注释会误判；后续建议整理为独立电机配置，消除多处定义。

| 项目 | 当前有效值 | 适配含义 |

| 电机 | LJW8115 KV76，36槽42极，21极对 | 不是旧5210的14极对 |
| 板端供电 | 24V/6S初次调试，欠压19.8V、过压27V | 电机资料的48V额定值不是这块板的可用输入电压 |
| 电流上限 | 4A | 未放开到资料12A额定、36.5A峰值 |

| 扭矩系数 | 0.125Nm/A初值 | 厂家电流定义与固件iq定义尚待核实，不能保证绝对扭矩准确 |
| 相电阻／相电感初值 | 0.0735Ω／28.5µH | 星形线电阻147mΩ、最小线电感57µH各除以2；尚待实测 |

## 3. 已对齐的CAN报文，与尚未对齐的物理限制

固件 [dm_can.h](../2.Firmware/FalconFoc/MODULES/can_comm/dm_can.h)、Python GUI/测试脚本及C++ [dm_protocol.h](falconfoc_studio/src/dm_protocol.h)使用相同的基础量程：

| 字段 | 线上定义 | 备注 |
|---|---|---|
| 位置P | ±50rad，16bit | 内部使用turn，CAN边界转换 |
| 速度V | ±300rad/s，12bit | 编码范围不代表允许转到该速度 |
| 力矩T | ±0.3Nm，12bit | 指令和反馈共用此量程 |
| Kp | 0～500 | MIT刚度，Nm/rad，不是固件位置环P |
| Kd | 0～5 | MIT阻尼，Nm/(rad/s)，运行时另有固件钳位 |
| CAN ID | MIT 0x01，位置速度0x101，速度0x201，反馈0x00 | 当前固件编译期固定；GUI改ID不会自动修改固件 |

### A01：力矩指令／反馈量程不足（高优先级）

当前内部电流限幅与Kt对应约 `4 × 0.125 = 0.5Nm`，但CAN力矩量程仍是±0.3Nm。直接MIT前馈最多表达±0.3Nm；MIT刚度/阻尼项等控制计算仍可能请求更大电流。反馈在 `DM_SendFeedback()` 中用 `iq × Kt` 计算，再钳位编码到±0.3Nm。

因此，上位机显示“0.3Nm平台”不一定说明实际估算扭矩恰好只有0.3Nm，也可能是报文饱和。这个值本身还是电流模型估算，不是扭矩传感器测量。

待改：制定带版本的协议配置，固件、两套GUI、测试脚本及保存数据的元信息同步更新。不能只改GUI的 `T_MAX`，否则同一字节会被双方解释成不同的力矩。初期可保留旧协议，但必须明确标注反馈范围及饱和状态。

### A02：4010的Kd阈值仍在使用（高优先级）

Python和C++均保留 `MIT_KD_SAFE=0.016` 及4010稳定性说明；固件 `MIT_KD_TURN_MAX=0.1`，折算线上约 `0.1/(2π)=0.015915`。两套GUI的Kd滑块可到0.1，协议甚至能编码到5，但超过固件阈值的请求会被钳位。

这不是KV76测得的稳定边界。不能仅按Kt比例放大Kd后宣布适配，也不能把固件速度PI增益当成MIT阻尼增益。需要核实电流定义、编码器噪声、负载惯量和采样延迟，再测闭环稳定性。GUI应分别展示请求值、已知钳位值和实测验证状态。

### A03：输入范围与单位没有统一配置（高优先级）

C++速度滑块为±50rad/s，MIT速度滑块为±20rad/s，这两者没有超过当前600rpm配置；不能笼统声称所有旧滑块都越限。但Python快速输入、波形发生器和导入预设没有统一的KV76限幅层，CAN速度／位置速度处理函数直接解析float并转换，未在这些入口统一拒绝NaN/Inf或按KV76限幅。

待改：统一校验所有入口，包括手工输入、滑块、预设、波形和CLI。区分协议可编码范围、控制模式限幅和初次调试范围。CAN线上使用rad/rad/s；固件内部使用turn/turn/s，换算为 `rad = turn × 2π`、`rpm = turn/s × 60`。

## 4. 操作和掉线保护：不能把界面行为当成停机保证

### A04：查询帧会喂通信看门狗（最高优先级）

[dm_can.c](../2.Firmware/FalconFoc/MODULES/can_comm/dm_can.c)在 `DM_RxCallback()` 开头更新 `g_can_last_rx_ms`，然后才识别命令。查询帧 `FF FF FF FF FF FF FF 00` 虽不更改目标，但同样刷新掉线计时。

C++ `maybe_stream()` 在关闭Stream后仍以20Hz查询；Python也有持续查询功能。因此，**取消Stream或只留下查询窗口，不保证200ms后停止电机；最后一个控制目标可能继续有效。** 现有README中的“零副作用查询”和“停止连续发送即停机”叙述不能作为操作保证。停止应显式发送DISABLE并观察反馈，不能只取消发送复选框。

待改：固件区分“收到通信”和“收到有效运动命令”的时钟；GUI提供独立停止动作。验收需包含“控制流停了但查询流继续”和“第二个客户端仍在查询”两种情况。

### A05：使能、默认目标、清错和重新连接缺少KV76保护流程

- C++默认MIT参数为P=0、Kp=2、Kd=0.01。若启用Stream，当前位置不为0时可能产生回零力矩；不能把默认界面理解为静止无输出。
- 固件ENABLE直接设置RUNNING，上位机不能把它当作固件已完成所有标定／故障前置条件的证明。
- CLEAR_ERR清理目标后进入IDLE并重新初始化；若新电机标定无效，可能进入自动标定，并非单纯清除界面提示。
- “Set Zero”修改软件位置参考，不是编码器电角度零位标定，也不等同于持久保存。
- 关闭窗口、断开CAN、取消Stream、发送DISABLE是不同操作，应逐一验证，不应互相替代。

待改：提供未标定／待使能／运行／故障的明确状态，开始保持前采样当前位置，默认不自动恢复旧目标；故障后不自动重新使能。

### A06：测试、齿槽标定和唱歌按钮会主动驱动

`foc_test.py`的测试会使能、运行，并周期性重发ENABLE；默认组合包含旧Kd测试（含0.3）。`test_cli.cpp`会主动发送3rad/s速度。它们不能用于“先看看有没有连接”的只读检查。

GUI的Cogging Cal发0xFA，是齿槽标定；USB `calib=1`是另一条重标定流程，二者不同。C++的Sing发0xF9，也会驱动电机。固件在齿槽标定期间跳过常规200ms通信掉线判断，所以不能用停止CAN流来保证标定停止。

待改：把连接探测与运动测试分开；标定和唱歌入口标明动作与停止方式；验证中止是否真正停止PWM并清理标定状态。不要直接复用4010/5210测试结果作为KV76验收。

## 5. USB文档与实现存在明确差异

### A07：USB速度／位置单位标错（最高优先级）

[USB_HOST_INTERFACE.md](../2.Firmware/FalconFoc/USB_HOST_INTERFACE.md)把速度、位置写为rad/s和rad，但当前 `vofa.c`：

- 遥测通道7直接发送 `vel_estimate_`，实际为 **turn/s**。
- 遥测通道8直接发送 `pos_estimate_`，实际为 **turn**。
- `set_vel=`、`set_pos=`直接写内部变量，没有CAN入口的除以2π处理，实际分别是 **turn/s、turn**。

例如按旧文档发 `set_vel=6.283` 想得到约1turn/s，代码实际写入约6.283turn/s，差约6.283倍。上位机必须按实际协议换算，或将固件USB协议改为明确版本的SI单位；修改前后的客户端不可混用。

### A08：USB不是完整的CAN替代控制通道

USB接收函数没有刷新CAN运动看门狗；`motor_enable`代码仍被注释。发 `set_ctrl_mode=`只改变模式，不能当作使能动作。`set_Iq=`写设定值也不意味着该设定会在所有控制模式中持续生效。

`set_current_ctrl_bw=`仅更新字段，本处理分支不立即重算PI增益；现有算法使用rad/s，旧USB文档写Hz。界面不得收到写命令就显示“增益已更新”。需要补充应答、参数回读和何时生效的约定。

当前解析按USB接收块使用 `strstr/atof`，没有完整的按行累积和逐条拆分协议；不能假设带换行就自动支持任意粘包、拆包或多命令连续发送。后续USB上位机适配应同时补接收协议测试。

## 6. 遥测、FFT和多电机信息不足

### A09：缺少配置协商和实际状态回读

现有DM反馈无法报告电机型号、21极对、Kt、电流上限、标定magic、固件版本或实际采用的Kd。GUI选择一个“KV76”标签也不能证明板端运行同一配置。应增加只读配置查询，连接时比较协议版本与电机配置，并在不匹配时禁止发送运动命令。

当前反馈两个温度字段来自同一颗NTC，并不是分别测得的MOS与转子温度。没有独立转子测温时不能据此证明绕组温度合格。

### A10：频谱、位置范围和多电机显示需校验

C++的FFT采样率字段默认50Hz，而空闲查询是20Hz；发送率也可以改变。采样率配置与真实采样不符会使频谱横轴错误。应按时间戳／实测帧率处理采样，明确抖动、丢帧和重采样策略。

位置反馈仅能编码±50rad，连续多圈运动会超量程；不能把饱和后的显示当成实际多圈位置。GUI应说明范围或扩展协议。

C++接收流程按主机反馈ID 0接收，未在应用该反馈前按用户选择的电机ID过滤；多电机共用该反馈ID时有混入风险。Python当前也按固定反馈ID工作。现阶段以单电机为前提；多电机适配需同时调整ID配置和反馈过滤。

## 7. 建议的适配顺序与验收标准

以下全部是后续工作，本文没有完成这些代码修改或硬件测试。

| 顺序 | 工作 | 验收证据 |
|---|---|---|
| P0 | 明确停机行为，分离查询心跳与运动看门狗 | 停止运动流但保留查询时按规定停机；显式停止有效；断连／重连不恢复旧目标 |
| P0 | 统一USB单位与命令生效语义 | CAN与USB对同一物理速度／位置读写一致；分包粘包测试通过 |

| P1 | 同步扭矩量程与反馈饱和显示 | 固件与Python/C++边界编码解码一致，旧量程配置被识别为不兼容 |
